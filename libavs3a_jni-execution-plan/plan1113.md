# 基于 `Sourcecodeforplayer\av3adecoder` 重构 SDK 的详细方案

> 2026-11-13 修订：按补充要求，将“JNI 暴露接口无缝替换”和“最终单 SO”作为硬约束。原方案中升级 v3、双 SO 动态加载及新增必需接口的建议，由本文对应章节替代。

## 一、结论与硬约束

实施路线：**保留现有 Java/JNI v2 接口，重写其内部实现；将安全化后的 av3adecoder 源码、模型、Native core 与 JNI 静态链接到同一个 `libavs3a_jni.so`。**

### 1.1 JNI 和业务调用无缝替换

- `System.loadLibrary("avs3a_jni")` 不变，最终 SONAME 为 `libavs3a_jni.so`。
- `com/inlz/avs3a/NativeBridge` 类名、16 个 native 方法名、描述符、static 属性不变。
- `API_CONTRACT_VERSION = 2`、`jniContractVersion = 2`、`nContractVersion() == 2` 不变。
- PCM/编码帧信息仍分别使用 8/11 个 `long`，字段顺序、单位、语义不变。
- 现有返回值、错误码、布局 ID、flag、句柄、epoch 和缓冲区所有权契约不变。
- 现有 Java public 方法、返回类型和业务调用顺序不变，不要求业务新增初始化、模型准备步骤或回调。
- 修复违背既有契约的错误，不把历史实现缺陷作为必须保留的行为；此类差异必须记录并测试。

### 1.2 单 SO 的准确含义

**每个目标 ABI 只有一个 SDK 运行时 SO：`libavs3a_jni.so`。**

```text
arm64-v8a/libavs3a_jni.so
armeabi-v7a/libavs3a_jni.so
```

两个 ABI 的机器码不同，不可能由一个 ELF 同时运行在 ARM64 和 ARMv7。只交付某一 ABI 时，产物就是一个 `.so` 文件；通用 AAR 中则为每个 ABI 各一个同名 SO。

- 不再生成、打包或运行时依赖 `libavs3a_decoder.so` / `libAVS3AudioDec.so`。
- C++ runtime 使用静态链接，不额外分发 `libc++_shared.so`。
- 默认模型内嵌，不依赖外置 `model.bin` 才能完成正常解码。
- Android 系统提供的 libc/libm/liblog 等动态依赖不属于额外交付文件，按白名单检查。
- `.a`、object、unstripped SO、符号包和测试工具允许作为构建/调试产物，但不属于额外运行时依赖。

### 1.3 兼容承诺边界

现有 `Avs3Sdk.open()` 会在进入 JNI 前调用 `RuntimeVendorVerifier`，强制查找并校验旧 `libavs3a_decoder.so`。因此，**“旧 AAR/全部旧 Java 字节码完全不变，仅替换一个 SO”与“删除独立 decoder SO”在现有实现下不能同时成立。**

本方案采用可执行的兼容范围：

1. 更新 SDK 内部 Java 实现和 AAR，业务源代码及已编译客户端调用签名不变。
2. 冻结的旧 `NativeBridge` 声明可直接绑定新 SO，不依赖新增 native 方法。
3. 验证旧业务客户端二进制与新 SDK 的兼容性；不声称完整旧 AAR 可直接配单 SO 使用。
4. 当前 SDK 的 ELF 导出入口只有版本脚本公开的 `JNI_OnLoad`；不承诺继续提供旧 decoder 独立 C 导出函数。

本轮只更新实施方案，未修改实现、编译 SO 或进行设备测试。

## 二、现状与替换影响

### 2.1 当前 SDK 与旧库存在深度绑定

目前打包的解码库为：

```text
sdk/src/full/jniLibs/
├── arm64-v8a/libavs3a_decoder.so
└── armeabi-v7a/libavs3a_decoder.so
```

SDK 的绑定不仅包括库名，还包括：

| 绑定项 | 当前实现 | 替换影响 |
|---|---|---|
| 导出函数 | `Avs3AllocDecoder`、`Avs3InitDecoder`、`Avs3Decode` 等 | 新源码接口不完全相同 |
| 私有结构体 | 按 ARM64/ARMv7 的固定偏移读写 | 不能继续用于新源码构建产物 |
| 模型 | 外置 `model.bin`，初始化时传路径 | 新源码默认使用内嵌模型 |
| 码流解析 | 固定支持 profile 0、7 字节帧头 | 对象/混合模式需要不同帧头 |
| 输出结构 | PCM + 固定扬声器布局 | 无法完整表达对象信号和 HOA |
| 文件校验 | Java 中写死旧 SO 的 SHA256 和大小 | 新库会被直接判定不匹配 |
| 发布校验 | 锁定旧 vendorId、ABI 偏移和文件指纹 | 必须同步重构 |
| 能力查询 | 部分状态由常量推导 | 不能准确反映新库实际能力 |

相关实现：

- [vendor_api.h](D:/gitlab/libavs3a_jni/native/src/vendor_api.h)
- [vendor_backend.cpp](D:/gitlab/libavs3a_jni/native/src/vendor_backend.cpp)
- [RuntimeVendorVerifier.java](D:/gitlab/libavs3a_jni/sdk/src/main/java/com/inlz/avs3a/RuntimeVendorVerifier.java)

一个明确的不兼容点：

```c
// 现有 SDK 对旧库的调用约定
void Avs3InitDecoder(void* decoder, const char* modelPath);

// 新源码中的实际声明
int Avs3InitDecoder(
    AVS3DecoderHandle decoder,
    FILE** modelFile,
    const char* modelPath);
```

即使符号名相同，直接调用仍然会发生参数不匹配。

### 2.2 新源码提供的能力和限制

新源码已有四个封装入口：

```c
avs3_create_decoder(...)
avs3_destroy_decoder(...)
parse_header(...)
avs3_decode(...)
```

同时提供 `Avs3DecoderLib*` 系列接口。

但这两组接口都不能不经改造直接作为稳定 SDK ABI：

- 暴露内部类型。
- 部分输入没有长度或容量参数。
- 初始化错误传递不完整。
- 封装中混有命令行、文件和 WAV 输出逻辑。
- 尚缺稳定的能力、配置、元数据和诊断接口。

接口位置：[avs3_decoder_interface.h](D:/gitlab/Sourcecodeforplayer/av3adecoder/avs3Decoder/include/avs3_decoder_interface.h)。

已确认的源码能力：

| 项目 | 源码现状 | SDK 设计原则 |
|---|---|---|
| 单声道、立体声、多声道 | 有解码路径 | 保留并验证现有能力 |
| 纯对象音频 | 有相关路径，但封装存在校验冲突 | 内部修复和验证；本次旧接口仍明确拒绝 |
| 声床 + 对象 | 有解码路径 | 本次旧接口明确拒绝，不冒充普通多声道 |
| HOA | 有 1～3 阶相关配置和解码路径 | 内部可逐阶验证；不通过本次旧接口开放 |
| 静态/动态元数据 | 有解析结构和实现 | 保留内部解析；对外扩展另行设计 |
| PCM | 当前封装输出交织 `int16` | 默认明确为 S16，不宣称原生 S24 |
| 最大信号通道数 | `MAX_CHANNELS = 16` | 所有组合均受总数上限约束 |
| 10.2、22.2 | 枚举存在，但码率表为 `NULL` | 继续明确拒绝，不能视为支持 |

**有源码分支不等于已经完成产品级验证。** 采样率、码率、神经网络类型、内容类型的组合，需要单独建立支持矩阵。

### 2.3 模型可以平滑兼容

已核对：

- 新源码的 `avs3Decoder/model.bin`：79,930 字节。
- SHA256 与当前 SDK 锁定的 `model.bin` 相同。
- `model.h` 内的模型数据经源码对应的 XOR 转换后，与该文件一致。

因此可以采用：

> **不新增必需调用：现有 prepareBundledModel/open 调用链默认使用内嵌模型，prepareModel/open 继续支持经过校验的外置同版本模型。**

不需要为了替换解码库而强制业务重新分发一套不同模型。

但“模型相同”不代表两套解码实现的 PCM 必然逐字节一致，仍须验证。

## 三、重构范围与兼容优先级

### 3.1 本次“完整实现”的范围

完整实现并验证当前 SDK 已有的所有接口：

- `Avs3Sdk` 的能力查询、模型准备、打开会话、创建解析器。
- `Avs3Session` / `Avs3FrameParser` 的输入、接收、EOS、flush、close。
- `QueueResult`、`PcmResult/PcmInfo`、`FrameResult/EncodedFrameInfo` 的完整语义。
- `Avs3Exception`、所有既有错误码、公开布局和常量。
- `NativeBridge` 的全部 16 个方法，包括诊断和版本查询。
- 原有 profile 0、NN 0/1、S16 源精度及已支持的普通声道布局。
- 分片输入、背压、完整帧输入、时间戳、epoch、并发和资源回收。

不接受“SO 编译成功但某些接口仍返回固定成功或空结果”作为完成。

### 3.2 不为新增能力破坏旧接口

当前固定的 8/11 槽位及 `PcmLayout` 无法完整表达对象音频、HOA 和动态元数据。本次不得：

- 扩大旧 JNI 数组或重解释既有字段。
- 将对象/HOA 信号伪装为普通多声道 PCM。
- 借 `flags`、PTS、epoch 或未知布局 ID 传递新数据。
- 将二进制音频元数据塞进 `nBuildInfo()`。
- 在同一冻结的 `NativeBridge` 注册表中加入旧类没有的方法，否则旧类的 `RegisterNatives` 会失败。

对象/混合/HOA 的算法与元数据解析可保留在内部并开展测试，但旧入口仍返回既有 `UNSUPPORTED_MODE`。对外开放这些能力是后续独立、可选的兼容扩展，不作为本次“现有 JNI 完整实现”的冒充成果。

若后续需要开放，另行设计可选扩展类/协议，不能回写本次冻结的 v2 契约。

### 3.3 不纳入的职责

不引入解复用、网络、AudioTrack、播放器时钟、空间/双耳渲染、头部跟踪或编码器。`av3a_binaural_render` 和 FFmpeg 不成为单 SO 的依赖。

## 四、目标架构：一个对外 SO，内部静态分层

### 4.1 运行时结构

```text
现有业务 / Media3 集成（调用方式不变）
                │
                ▼
现有 Java API（SDK 内部加载/模型逻辑更新）
                │
                ▼
libavs3a_jni.so                       唯一 SDK 运行时 SO
├── JNI_OnLoad + 原 16 个 RegisterNatives 方法
├── Registry / Session / Framer / Timeline
├── 静态 SourceDecoderBackend / 安全适配层
├── av3adecoder 解码算法
└── 内嵌模型和构建身份
```

取消 decoder 的 `dlopen/dlsym/dlclose` 流程。内部适配层以静态函数/类型化调用连接源码，不再有运行时跨 decoder SO 的 ABI 握手。

### 4.2 编译边界

- `avs3a_core`：可继续为 STATIC target，包含队列、解析、时间线等。
- `avs3a_reference_decoder`：STATIC 或 OBJECT target，包含显式列出的 decoder/common 必需源码。
- `avs3a_jni`：full 构建唯一的 SHARED target，链接上述内部模块和内嵌模型。
- 所有静态对象启用 PIC，隐藏内部符号。
- 不能把原 Makefile 中的全部 `*.c` 直接 glob 进产品库，避免带入 CLI、main、encoder 和 WAV 工具。

### 4.3 移除旧私有偏移 ABI

- 删除主构建对 `AbiAccessor` 和旧字段偏移生成代码的依赖。
- 不从裸句柄偏移读取 bitstream 或写入配置。
- 仅在源码适配模块中通过真实头文件访问内部类型。
- JNI 和会话层只持有内部不透明实例或 `DecoderBackend`。
- 初始化、解码、reset、destroy 的输入长度、输出容量和错误返回必须明确。
- 内部接口可以重构，不需要向 ELF 导出 `avs3a_decoder_*` 或参考库函数。

### 4.4 full / bridge 的处理

最终交付以 **full 单 SO** 为准。为保持现有工程任务和 parser-only 用途，可保留 bridge 构建变体：

| 变体 | 运行时 SO | 能力 |
|---|---|---|
| full | 仅 `libavs3a_jni.so` | JNI + parser + decoder + 内嵌模型 |
| bridge | 仅 `libavs3a_jni.so` | JNI + parser，无 decoder/model，能力明确不可解码 |

两者为互斥替代产物，不能在一个应用中同时打包。bridge 不再通过外置 decoder 动态升级为 full；需要解码时整体替换为 full 变体，业务 API 不变。

## 五、源码移植和安全化

这是整个方案的关键工作，不应仅在 JNI 外层增加异常捕获。

### 5.1 拆分命令行与库实现

当前 `decoder.c` 同时包含 `main()` 和库入口。

建议拆分为：

- CLI：仅用于参考解码和测试。
- 解码核心：算法和内部状态。
- SDK 适配层：稳定接口及安全检查。
- WAV 文件工具：仅测试工具使用。

Android 库不应包含：

- 命令行参数处理。
- WAV 文件输出职责。
- 调试文件路径。
- 重定向标准输出。
- 非必要的逐帧 `printf`。

### 5.2 初始化与资源管理改造

当前源码存在多处 `exit(-1)` 和运行时断言。见：

[avs3_init_dec.c](D:/gitlab/Sourcecodeforplayer/av3adecoder/avs3Decoder/src/avs3_init_dec.c)。

必须改为：

- 分配失败逐层返回 `NO_MEMORY`。
- 初始化失败可以完整回滚。
- 未初始化和部分初始化实例均可安全销毁。
- 元数据状态清零初始化。
- 神经网络模型加载错误可以返回。
- 不通过关闭断言来掩盖非法状态。

验收覆盖：

```text
创建后立即销毁
首帧前 flush
初始化中任意分配失败
部分初始化后销毁
解码失败后 flush
重复 close
```

### 5.3 有界帧头解析

新源码 `parse_header()` 存在如下风险：

- 先要求至少 9 字节，虽然部分模式实际帧头只有 7 字节。
- 若干索引未充分校验即访问表。
- 不支持布局可能访问 `NULL` 码率表。
- 对象数、声床通道数和 HOA 阶数需要限制。
- 纯对象模式使用 `CHANNEL_CONFIG_UNKNOWN`，却会被后续通用校验拒绝。

建议保留一个**独立、无解码器状态依赖的安全帧头解析模块**，由会话层和静态解码适配层共享规则，不形成独立 SO。

源码各模式的帧头长度如下；本次旧接口仅接纳原有 profile 0，其他模式识别后返回 UNSUPPORTED_MODE，不能因解析器可识别而自动开放解码：

| 类型 | 帧头长度 |
|---|---:|
| 普通声道 | 7 字节 |
| HOA | 7 字节 |
| 纯对象 | 8 字节 |
| 声床 + 对象 | 9 字节 |

统一检查：

- 同步字、codecId、保留位。
- profile、NN 类型、采样率索引。
- 码率索引及对应表项。
- source precision。
- 对象数、声床数、总信号数。
- HOA 阶数。
- 帧长度计算溢出和上限。

新旧 profile 0 的表可做自动交叉核对，但不能继续把整个协议限定为 7 字节帧头。

### 5.4 CRC 与 payload 安全

当前封装的帧完整性和 CRC 检查有被注释或 `#if 0` 关闭的情况。见：

[decoder.c](D:/gitlab/Sourcecodeforplayer/av3adecoder/avs3Decoder/src/decoder.c)。

建议：

- 默认执行完整帧 CRC 校验。
- 不完整输入返回 `NEED_INPUT`。
- EOS 时剩余不完整帧返回 `TRUNCATED_FRAME`。
- 完整帧模式下出现额外字节或多帧，返回契约错误。
- 检查 bit reader、熵解码、元数据数组等内部访问边界。

**CRC 不能替代 payload 边界检查**：CRC 正确的恶意或异常帧同样可能包含非法内部字段。

### 5.5 不直接放大旧限制

当前 SDK 有：

```text
payloadBits <= 32767
完整帧 <= 4096 bytes
```

新源码虽然有 12,300 字节 bitstream 缓冲区，但部分 mono/stereo 位预算仍使用 `short`。

因此：

1. 第一阶段保留保守限制。
2. 审计位预算和长度传递链。
3. 必要时改为 `int32_t`/`uint32_t`。
4. 对新增范围进行边界、模糊和真实解码测试。
5. 本次无缝替换不提高公开上限；范围扩展须在后续兼容扩展方案中单独验收。

不能因为内部数组更大，就直接宣布高码率对象组合全部可用。

### 5.6 多实例和随机状态

源码中的噪声填充等路径使用全局 `rand()`。

需要：

- 排查所有共享可变状态。
- 将随机状态改为实例私有，或明确受控的兼容实现。
- 定义 reset/flush 后的随机状态。
- 并行实例不能改变彼此的解码结果。

如果随机实现变更导致 PCM 差异，必须记录为明确的算法适配变化，并重新冻结参考输出，不能把它当作测试噪声忽略。

## 六、冻结现有 Java/JNI 契约

### 6.1 契约基线

以当前 `protocol/jni-contract.json`、`NativeBridge.java`、`NativeCalls.java`、`JniCalls.java` 和公开 Java 类为基线，发布前执行自动差异检查。

```text
apiContractVersion          = 2
jniContractVersion          = 2
nativeClass                 = com/inlz/avs3a/NativeBridge
pcmMetadataLongs            = 8
encodedFrameMetadataLongs   = 11
ELF SONAME                  = libavs3a_jni.so
ELF export version node     = AVS3A_JNI_1
ELF API export              = JNI_OnLoad
```

SDK 发布版本和 backend/source revision 可以变化；不得将 JNI/API 契约升为 3。当前版本脚本继续使用 `global: JNI_OnLoad; local: *;`，不改为公开 `Java_*` 或 decoder C API。

### 6.2 16 个 native 方法逐项冻结

全部为 static，完整描述符必须匹配：

| 方法 | JNI 描述符 | 实现要求 |
|---|---|---|
| `nContractVersion` | `()I` | 始终返回现有契约版本 2 |
| `nProcessAbi` | `()I` | ARM64=1、ARMv7=2，其他沿用原编码 |
| `nCapabilities` | `()J` | 保留既有返回约定；当前未定义 bit，不能私自新增 bit 含义 |
| `nBuildInfo` | `()Ljava/lang/String;` | 保留既有 key=value 格式和字段，可追加诊断键 |
| `nCreate` | `(Ljava/lang/String;Ljava/lang/String;J)J` | 参数个数/顺序不变；内部创建静态 backend |
| `nQueue` | `(J[BIIJJI)I` | 原输入、背压和 epoch 语义 |
| `nReceive` | `(J[BII[J)I` | 原 PCM 输出及 8 槽位信息 |
| `nEnd` | `(J)I` | 标记 EOS，先排空后结束 |
| `nFlush` | `(JJ)I` | 清状态，严格递增 epoch |
| `nRelease` | `(J)V` | 幂等释放，不改变方法返回类型 |
| `nParserCreate` | `(J)J` | 创建无需 decoder/model 的 parser |
| `nParserQueue` | `(J[BIIJJI)I` | 与旧 parser 输入语义一致 |
| `nParserReceive` | `(J[BII[J)I` | 原完整帧输出及 11 槽位信息 |
| `nParserEnd` | `(J)I` | 原 parser EOS 语义 |
| `nParserFlush` | `(JJ)I` | 清 parser/PTS，更新 epoch |
| `nParserRelease` | `(J)V` | 幂等释放 parser |

`nCapabilities()` 当前实现为 0，契约没有 bit 定义，本次维持这一保留值；不能凭空将其改为新的功能位协议。现有 `Avs3Sdk.capabilities()` 的完整能力状态由既有 `nBuildInfo()` 追加的内部构建信息和真实的打包/身份/模型检查得到，不以该保留值冒充检测结果。

`nBuildInfo()` 保留 `sdkVersion/sourceCommit/apiContract/jniContract/processAbi/abiVerified/dialectVerified/vendorId` 等键。身份值随实现变化如实更新；可追加 `backendKind=linked_reference`、`decoderSourceCommit`、`modelSha256`、`embeddedModelReady` 等键，不伪造旧 vendor 身份，也不把“编译进库”当作“真机已验证”。

### 6.3 nCreate 的历史参数适配

保持签名：

```java
long nCreate(String modelPath, String verifiedVendorPath, long epoch);
```

内部语义明确为：

- `modelPath` 非空：读取并再次验证外置同版本模型，初始化必须实际使用该内容；缺失/损坏仍返回原模型错误。
- `modelPath` 为空或 null：full 使用已校验的内嵌模型；这是 SDK 内部新增的模型来源分支，不改变旧非空调用。
- `verifiedVendorPath`：保留为历史兼容参数。接受旧合法路径字符串，不再用它加载第二个库；更新后的 SDK 内部传空字符串。它不再是选择任意外部解码器的入口。
- backend 身份验证改为当前已加载单 SO 的构建身份和打包指纹验证，不依赖历史参数“证明”库可信。
- 返回值仍为正数句柄或现有负错误码，不以 0 表示成功。
- 非法 epoch、内存失败等检查保留；bridge 没有 decoder，仍返回既有后端缺失错误，不创建假解码会话。

该参数角色变化必须写入 SDK 内部迁移说明并增加直接 JNI 回归测试；无缝指方法绑定和业务使用方式兼容，不包括继续支持任意旧外部 decoder 注入。

### 6.5 Java API 和模型的无缝适配

保留所有现有 public 签名，包括：

```java
Avs3Sdk.capabilities(context);
Avs3Sdk.prepareBundledModel(context);
Avs3Sdk.prepareModel(context, modelSource);
Avs3Sdk.open(verifiedModel, epoch);
Avs3Sdk.newFrameParser(epoch);
```

旧业务代码继续工作：

```java
VerifiedModel model = Avs3Sdk.prepareBundledModel(context);
try (Avs3Session session = Avs3Sdk.open(model, epoch)) {
    session.queueInput(data, 0, data.length, ptsUs, epoch, 0);
    PcmResult result = session.receivePcm(output, 0, output.length);
}
```

模型处理：

1. full 的 `prepareBundledModel()` 校验当前单 SO 的内嵌模型身份，返回 opaque `VerifiedModel`；内部路径为空代表内嵌来源，不再强制提取 asset。
2. 当前公开契约明确 `VerifiedModel` 不提供私有文件路径访问，本次可以修改内部来源表示，但须更新“将 bundled asset 写入磁盘”的实现说明及内部测试。
3. `prepareModel()` 继续读取、SHA 校验和准备外部模型，保留既有缺失/损坏/IO 错误行为；不能变成忽略参数的空实现。
4. 非空外部模型在 Native 初始化前重新校验并形成稳定快照，避免只检查 Java 文件路径后发生变化。
5. 默认 full AAR 和单 SO 使用链不需要单独 `model.bin`；旧宿主即使残留该资源也不会改变内嵌路径。
6. bridge 没有内嵌模型，`prepareBundledModel()` 仍报告模型不可用；parser 不依赖该方法。

`Avs3Capabilities` 不增加必需字段或修改 getter；`vendorPresent/vendorFingerprintMatched/vendorAbiVerified` 保留旧名称，其检查对象从“外置 vendor 库”改为“单 SO 内的解码 backend 及其构建身份”。这种内部提供方变化需明确文档化，不能继续宣称检查了不存在的旧库。`decodeImplementationReady` 必须来自完整检查，不能仅判断 CPU 为 ARM 即返回 true。

### 6.6 会话、解析器、PTS 与 EOS 语义

| 场景 | 兼容要求 |
|---|---|
| queue 成功 | SDK 已持有独立输入副本，调用者可复用输入数组 |
| 背压 | 本次输入全部未接收，可完整重试 |
| 完整帧 flag | 保留独立完整 sample 校验，以及旧契约允许的补齐已有单个 partial frame；拒绝时不修改队列 |
| 输出太小 | 保留同一输出，不重复解码、不改变 PTS |
| 数据不足 | NEED_INPUT；不向调用者输出部分 PCM |
| EOS | 排空已接收数据，非 padding 残缺帧报 TRUNCATED_FRAME |
| EOS 后输入 | INVALID_STATE，直到 flush |
| flush | 清输入、pending PCM/frame、失败状态、解码状态、PTS 和内部元数据 |
| epoch | 包括初始 epoch=0，均严格校验；flush 要求 newEpoch 更大 |
| 配置变化 | 保留 UNSUPPORTED_CONFIG_CHANGE，不自动重建并掩盖变化 |
| close | 幂等，后续访问保持 CLOSED_OR_INVALID_HANDLE |

显式 PTS 按输入字节位置关联，未指定 PTS 的帧按累计采样数推导，flush 后回到 TIME_UNSET。保留无累积截断误差的计算，不因换 backend 改变队列和时间线逻辑。

EOS 不擅自插入静音或尾帧；编码延迟、尾部 padding 和 gapless 仍需真实素材验证，不借本次替换宣称已解决。

另外必须实现一个 ELF 加载入口，它不计入上述 16 个 Java native 方法：

```cpp
extern "C" JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM* vm, void* reserved);
```

`JNI_OnLoad` 的要求：

1. 使用 `GetEnv(..., JNI_VERSION_1_6)` 获取当前线程的 `JNIEnv`。
2. 查找原类 `com/inlz/avs3a/NativeBridge`。
3. 一次注册第 6.2 节的原有 16 个方法，方法个数、顺序基线、描述符、static 属性可自动验证。
4. 成功返回 `JNI_VERSION_1_6`；取环境、查类、注册任一失败均返回 `JNI_ERR`，不能忽略异常后报告加载成功。
5. 正确清理局部引用；不缓存跨线程使用的 `JNIEnv*`。
6. 不在加载入口创建 decoder、准备外部模型、进行实际解码或加载第二个 SO。bridge 的 parser-only 加载不得依赖 decoder/model。
7. 不增加 `Java_com_*` 导出函数，不增加旧类没有的方法；`JNI_OnUnload` 不作为本次新增必需导出，session close 也不负责卸载整个库。

C++ 回调使用 `JNIEnv*`、`jclass` 作为前两个参数；后续采用 `jlong/jint/jstring/jbyteArray/jlongArray`，不能用平台相关的 `long` 代替 `jlong`。

### 6.8 所有 JNI 入口的通用规则

#### 6.8.1 句柄、线程与事务边界

- 成功句柄是 Registry 分配的正 `jlong`，不是直接公开的 C 指针；0 和负数永远不是有效句柄。
- Registry 记录 DECODER/PARSER 类型。类型化的 queue/receive/end/flush 调用遇到错误类型返回 `HANDLE_KIND_MISMATCH`；两个 void release 的特殊规则见对应条目。
- 查找、类型检查和摘除使用短锁；取到 `shared_ptr` 后再进行 session 操作，不在 registry 锁内解码或销毁。
- 句柄 ID 不回绕复用；耗尽时创建返回 `NO_MEMORY`，不能让过期句柄指向新实例。
- Java synchronized 不能替代 Native 检查，直接调用 JNI 或不同包装对象仍须线程安全。
- 参数校验失败、背压、完整 sample 校验失败时，不提交本次输入或更新 PTS/epoch。
- 非法句柄、参数、epoch 等可纠正的调用错误不应自动毒化原本正常的 session；码流/解码错误进入 FAILED 后，保存错误码，直到成功 flush 或 release。

#### 6.8.2 输入和输出数组

- 输入参数的 `off/len` 单位为字节；输出 `off/cap` 也为字节，不能把 cap 当作 sample 数。
- 先检查有符号值，再做不溢出的范围检查；不得先把负数转换为 `size_t`。
- 输入 `in == null` 仅在 `off == 0 && len == 0` 时允许，随后仍执行状态、epoch 和 flags 检查。
- 非空输入允许 `len == 0`，且 `off` 可等于数组长度；普通流模式下零长度成功调用不添加数据或 PTS 锚点。
- 输出 `out` 必须非 null，`cap == 0` 允许；`off == out.length` 仅在 cap 为 0 时有效。
- 为兼容现有 Native 实现，receive 的 `info == null` 允许，表示不复制元信息；Java SDK 正常调用仍总是提供 info。
- `info != null` 时，PCM 至少 8 槽位，编码帧至少 11 槽位；额外槽位不写，长度不足返回 `INVALID_ARGUMENT`。
- 输入复制进 Native 自有缓冲区，不保存 Java 数组地址；不在长时间解码期间持有 Critical 数组指针。
- READY 只写 `[off, off + 实际字节数)`；其他区域和超出有效槽位的 info 内容不修改。

#### 6.8.3 返回码和 JVM 异常

- 普通可处理失败通过既有负错误码返回；C++ `bad_alloc` 对应 `NO_MEMORY`，其他可处理内部异常对应 `INTERNAL`。
- JNI API 若产生 JVM pending exception，例如数组/字符串分配 OOME，保留该异常并尽快退出；只做允许的释放清理，不清除异常后伪装成功。
- `nBuildInfo()` 的 Java String 分配失败不能编码成负数，只能返回 null 并保留 JVM 异常；无异常的正常返回必须非 null。
- receive 先保留 Native pending 结果，再写 Java 数组；仅在所需 PCM/frame 和 info 复制全部成功后确认消费。
- prepare/copy/commit 在同一会话互斥保护或等价的世代校验下完成，flush/release 不能穿插导致旧 pending 被提交到新 epoch；不能只添加三个函数而放弃这段事务的并发保护。
- JVM 复制失败可能已经修改部分调用方数组，异常路径不得消费这些数组；Native 不丢 pending 帧，避免捕获异常后的重试跳帧。不能承诺 JVM 异常下两个独立数组的物理写入原子性。
- 禁止 `exit/abort`、跨 JNI 的 C++ 异常，以及释放无关实例。普通日志不包含输入音频或完整模型私有路径。

### 6.9 16 个方法的逐项实现要求

#### 6.9.1 nContractVersion：查询契约版本

```java
static native int nContractVersion();
```

- **职责**：返回编译时冻结的 API/JNI v2 对应版本值 2，供旧 `BridgeLoader` 校验。
- **状态/副作用**：full/bridge 一致；不创建句柄、不加载模型、不解码。
- **验收**：两个 ABI、两个变体均返回 2；SDK 发布版本变化不改变该值。

#### 6.9.2 nProcessAbi：查询实际进程 ABI

```java
static native int nProcessAbi();
```

- **职责**：按当前 SO 编译目标返回 ARM64=1、ARMv7=2；既有未知编码为 0。
- **要求**：不能用设备 `SUPPORTED_ABIS[0]` 推断进程位数，64 位设备运行 32 位进程仍返回 2。
- **验收**：ARM64/ARMv7 分别与 ELF 架构和进程位数匹配；host 测试替身不冒充设备验证。

#### 6.9.3 nCapabilities：保留的能力入口

```java
static native long nCapabilities();
```

- **职责**：本次维持现有未分配能力位的保留返回值 `0L`，不自行定义新的 bit 协议。
- **要求**：不做模型准备、不扫描外部文件、不创建 session；调用者不能把 0 当成完整可解码能力结论。
- **能力实现位置**：现有 `Avs3Sdk.capabilities()` 通过单 SO 实际身份校验及 `nBuildInfo()` 的已约定内部信息计算原有 getter。保留入口不等于允许 public capabilities 返回虚假常量。
- **验收**：重复调用稳定、无副作用；缺 decoder 的 bridge 与可解码 full 在 public capabilities 中正确区分。

#### 6.9.4 nBuildInfo：返回构建与后端身份

```java
static native String nBuildInfo();
```

- **职责**：返回 UTF-8 可表示的 `key=value\n` 文本，保留原键并按第 6.2 节追加单 SO、源码和模型身份。
- **要求**：`apiContract/jniContract` 均为 2；版本、sourceCommit、processAbi 与当前产物一致；full/bridge 不复用错误的 backend/model 状态。
- **生命周期**：可以缓存进程内不可变 Native 文本，每次返回独立的 Java String；不把某个外部模型 session 的状态写成全局模型准备状态。
- **错误**：Native 分配失败转换为受控 Java 内存异常；JNI 字符串分配失败保留 JVM 异常，不能返回截断或虚构成功文本。
- **验收**：原键仍可解析，追加键不破坏旧格式，文档中的验证状态与真实证据一致。

#### 6.9.5 nCreate：创建解码会话

```java
static native long nCreate(String modelPath, String verifiedVendorPath, long epoch);
```

- **参数**：`epoch >= 0`；模型来源和历史 vendorPath 的处理严格按第 6.3 节，不删第二个字符串参数。
- **流程**：检查参数/构建能力 → 解析并验证内嵌或外部模型形成稳定输入 → 创建源码 backend 与 Session → 设置初始 epoch → 注册 DECODER 句柄。
- **初始化时机**：创建时没有码流配置，不能猜采样率、声道、码率。配置相关的算法初始化延迟到 receive 取得第一帧之后；模型合法性可以在创建时提前确认。
- **返回**：成功为正句柄；负 epoch=`INVALID_ARGUMENT`，无 backend=`VENDOR_UNAVAILABLE`，ABI/构建契约不可用使用既有对应错误，模型失败使用既有模型错误，内存/句柄空间不足=`NO_MEMORY`。
- **失败回滚**：只有准备成功才发布句柄；失败不留下 Registry 项、文件句柄、模型或半初始化 decoder。
- **验收**：内嵌/外部模型成功、缺失/坏 SHA、epoch=0/负数、创建即销毁、创建即 EOS、逐处分配失败；成功创建本身不伪装为已解出 PCM。

#### 6.9.6 nQueue：提交压缩输入

```java
static native int nQueue(long h, byte[] in, int off, int len,
                         long ptsUs, long epoch, int flags);
```

- **参数**：h 为 DECODER；`epoch` 必须等于当前 session epoch；`flags` 仅允许 0 或 1。ptsUs 是微秒或 `TIME_UNSET`，不额外要求非负，也不将负 PTS 误当 epoch。
- **限制**：单次输入最多 `256 * 1024` 字节，超过返回 `INPUT_TOO_LARGE`；输入队列预算 `512 * 1024` 字节，无法完整接收本次输入返回 `BACKPRESSURE=1`。
- **流模式**：flags=0 允许任意分片，包括跨帧头、跨 payload 和一包多帧；成功不表示已经解码或 CRC 已通过。
- **完整 sample 模式**：flags=1 按第 6.6 节校验独立完整帧或补齐已有单个 partial frame；不能因为已有其他完整帧排队而误拒绝。失败返回 `COMPLETE_SAMPLE_CONTRACT`，不部分接收。
- **副作用**：成功时复制全部输入并按字节位置记录有效 PTS；队列拒绝时输入、时间戳锚点、累计字节计数整体不变。内存失败也不能只提交锚点不提交字节。
- **返回**：0=全部接收，1=全部未接收；不是消费字节数。关闭/类型/参数/epoch/EOS/FAILED 状态分别使用既有映射。
- **验收**：单字节输入、多帧输入、队列边界、零输入、零 epoch、flags 非法、完整帧补齐和拒绝后重试、成功后修改原 byte[] 不影响解码。

#### 6.9.7 nReceive：获取一帧 PCM

```java
static native int nReceive(long h, byte[] out, int off, int cap, long[] info);
```

- **参数**：h 为 DECODER；输出数组和可空 info 按第 6.8 节校验，不能因 Java 包装层已检查而省略 Native 检查。
- **流程**：优先使用 pending PCM；否则取一帧 → 校验帧/CRC/范围 → 首帧配置初始化或检查配置一致性 → 计算 PTS → 解码一次 → 验证 PCM 形状 → 保留 pending。
- **输出**：一次最多一帧 S16LE interleaved，`info[0..7]` 严格按第 6.4 节；不要把编码帧 4096 字节上限误用为 PCM 上限，例如 5.1 的 1024 samples/channel 需要 12288 字节。
- **空间不足**：返回 3；不写 out；`info[4]` 为需要的 PCM 字节数，其余槽位为同一 pending 帧元信息；下次扩大空间时返回同一帧，不重复解码或增加帧序号。
- **输入不足/EOS**：无完整输入且尚未 end 返回 0；已 end 且排空返回 2；残缺尾帧使用 `TRUNCATED_FRAME`，不是正常 EOS。
- **错误**：CRC/非法头、模式不支持、配置变化、初始化/解码/PCM 形状错误均使用既有错误码，进入对应失败处理；不能输出部分 PCM 后报告成功。
- **交付确认**：正常 READY=1 只在 Java 输出及要求的 info 复制成功后提交 pending 消费；JVM 异常遵守第 6.8.3 节。
- **验收**：0/小于/等于/大于所需容量、null info、额外 info 槽位哨兵、数组前后哨兵、重复 OUTPUT_TOO_SMALL、不同输入 PTS、CRC 错误、配置变化、输出复制异常注入。

#### 6.9.8 nEnd：结束解码器输入

```java
static native int nEnd(long h);
```

- **职责**：对 DECODER 标记输入结束，转入排空流程；不清队列、不丢 pending、不立即销毁 decoder。
- **返回**：正常返回 0；重复 end（未失败且未关闭）返回 0；无效句柄/类型错误/FAILED 返回对应已有错误。
- **后续**：nReceive 继续逐帧输出直至 EOS；nQueue 拒绝新输入；成功 nFlush 后允许再次输入。
- **验收**：空流 end、队列有多帧时 end、pending 太小时 end、重复 end、截断帧在 receive 阶段报告错误。

#### 6.9.9 nFlush：重置解码会话

```java
static native int nFlush(long h, long epoch);
```

- **参数**：此处 epoch 是 newEpoch，必须严格大于当前值；不满足时返回 `STALE_EPOCH`，包括负数及 0→0，且不修改会话。
- **职责**：对 DECODER 清除输入、PTS 锚点、pending PCM/frame、EOS、失败码、累计帧/样本计数、配置、算法历史和内部元数据，回到 WAITING_HEADER。
- **资源**：销毁/重建或完整 reset 配置相关 decoder 状态；保留同一公开句柄和已验证模型来源/稳定快照，不能重新打开旧 vendor 库。
- **失败态**：本方案按第 6.6 节允许 FAILED 经成功 flush 恢复；在恢复完成前不能只更新 epoch 而保留旧解码状态。
- **上界**：当前 epoch 已为 `Long.MAX_VALUE` 时没有合法更大值，调用者需 release 后新建，不能整数回绕。
- **验收**：首帧前 flush、解码后 flush、EOS/FAILED 后 flush、旧 epoch 输入拒绝、新 PTS 前为 TIME_UNSET、reset 后结果与对应新建会话基线一致。

#### 6.9.10 nRelease：释放解码会话

```java
static native void nRelease(long h);
```

- **职责**：只释放 DECODER 类型实例；在 registry 短锁内原子地“检查类型并摘除”，随后锁外执行 close。
- **兼容安全规则**：无效/已释放/负句柄为 no-op；错误类型也为 no-op，不得释放 PARSER。void 方法不能返回 `HANDLE_KIND_MISMATCH` 或新增必需的 Java 异常。
- **并发**：释放与正在进行的 receive/flush 安全串行；已取得共享引用的调用不能访问已释放内存；释放返回后新调用不得再取得此句柄。
- **资源**：释放 pending、队列、模型/算法实例等会话资源，不卸载共享的 `libavs3a_jni.so`，不破坏其他 session。
- **验收**：重复释放、随机句柄、错类型、多线程竞争、创建后立即释放、解码失败后释放、句柄再用得到 `CLOSED_OR_INVALID_HANDLE`。

#### 6.9.11 nParserCreate：创建独立帧解析器

```java
static native long nParserCreate(long epoch);
```

- **职责**：创建 PARSER Session，含 framer/时间线/输入队列，但不创建算法 decoder、不加载或校验模型。
- **返回**：epoch 非负时成功返回正句柄；负 epoch=`INVALID_ARGUMENT`；分配失败或 ID 耗尽=`NO_MEMORY`。
- **变体**：full/bridge 均可用，缺模型不影响创建；不强制复用 nCreate 的 vendor/model 前置条件。
- **验收**：无 decoder/model 环境、epoch=0/负数、并行 parser、多次创建释放、创建失败回滚。

#### 6.9.12 nParserQueue：提交待解析字节

```java
static native int nParserQueue(long h, byte[] in, int off, int len,
                               long ptsUs, long epoch, int flags);
```

- **职责**：h 必须为 PARSER，执行与 nQueue 相同的输入范围、256 KiB 单包/512 KiB 队列预算、epoch、flags、背压和 PTS 锚点规则。
- **差异**：仅缓存待分帧数据，不调用模型或音频解码器；不能为了代码复用而进入 DECODER 初始化路径。
- **返回**：0/1 和既有错误码与 queue 语义一致，不返回已消费字节数；零输入及完整 sample 的兼容行为一致。
- **验收**：复用输入边界/原子拒绝用例，增加 decoder 句柄错传和 bridge 无模型正常分帧。

#### 6.9.13 nParserReceive：获取一帧完整压缩数据

```java
static native int nParserReceive(long h, byte[] out, int off, int cap, long[] info);
```

- **职责**：优先使用 pending frame；否则扫描同步、解析帧头、检查帧长/CRC/支持范围、关联 PTS，返回完整编码帧，而不是只返回 payload。
- **输出**：READY=1 时原样复制完整 frame 字节到 out；11 槽位包含该帧的真实 frameBytes、payloadOffset、payloadBytes、bitrate、channelMode、layout 和 epoch。
- **空间不足**：返回 3，不写 out，`info[4]` 为完整帧所需字节数；保留同一 pending frame 供重试。
- **输入不足/EOS**：分别返回 0/2；坏帧、失步超限和尾部截断使用既有错误，不能输出坏帧当作 READY。
- **与 decoder 的区别**：parser 不初始化算法，也不为方便复用而增加“首帧后配置锁定”的限制；现有 parser 可按帧报告其支持范围内的配置变化，decoder 的 `UNSUPPORTED_CONFIG_CHANGE` 策略不能直接照搬。
- **范围**：能识别对象/HOA 帧头不代表旧接口可返回这些布局，仍按本次兼容范围拒绝。
- **验收**：输出与输入完整帧逐字节一致、头/payload 边界、不同支持布局逐帧信息、容量不足重试、info=null/短数组、bad CRC、无模型和 EOS 残留。

#### 6.9.14 nParserEnd：结束解析器输入

```java
static native int nParserEnd(long h);
```

- **职责**：仅接受 PARSER 句柄，标记输入结束，保留队列与 pending frame 等待 nParserReceive 排空。
- **返回**：正常/重复 end 返回 0，句柄/类型/FAILED 按既有规则返回负码；后续 queue 被拒绝直到 flush。
- **验收**：空流、整帧、多帧、残缺帧、OUTPUT_TOO_SMALL 后 end、重复 end；不依赖解码库能力。

#### 6.9.15 nParserFlush：重置解析器

```java
static native int nParserFlush(long h, long epoch);
```

- **参数**：h 为 PARSER；newEpoch 必须严格更大，非法递增返回 `STALE_EPOCH` 且不丢队列。
- **职责**：清除 pending frame、输入、扫描位置、已消费/排队字节计数、PTS 锚点、帧计数、EOS 和失败码，保留原句柄。
- **差异**：不调用算法 decoder 的 destroy/init，不能因没有模型而失败。
- **验收**：半帧中 flush、排队完整帧中 flush、EOS/FAILED 后恢复、初始 epoch=0、旧 epoch 拒绝、TIME_UNSET 恢复。

#### 6.9.16 nParserRelease：释放解析器

```java
static native void nParserRelease(long h);
```

- **职责**：原子检查 PARSER 类型并摘除，释放 parser 队列、pending frame 和时间线；无效/已释放/错类型句柄为 no-op。
- **禁止**：不能误删 DECODER 实例，不能调用与 parser 无关的模型销毁逻辑，不能卸载整个 JNI SO。
- **验收**：与 nRelease 对称的重复/并发/错类型/失败后释放测试；误传 decoder 句柄后原 decoder 仍可正常使用。

### 6.10 接口共享的状态和输出契约

#### 6.10.1 操作与状态

| 状态 | queue | receive | end | 合法 flush | release |
|---|---|---|---|---|---|
| WAITING_HEADER / READY | 校验后接收或背压 | READY / NEED_INPUT / TOO_SMALL / 错误 | 标记结束，返回 0 | 清状态并递增 epoch | 关闭 |
| DRAINING | INVALID_STATE | 排空、TOO_SMALL、EOS 或尾帧错误 | 幂等返回 0 | 恢复可输入 | 关闭 |
| ENDED | INVALID_STATE | 重复 END_OF_STREAM | 幂等返回 0 | 恢复可输入 | 关闭 |
| FAILED | 返回保存的失败码 | 返回保存的失败码 | 返回保存的失败码 | 清失败并恢复 | 关闭 |
| CLOSED / 已摘除 | CLOSED_OR_INVALID_HANDLE | CLOSED_OR_INVALID_HANDLE | CLOSED_OR_INVALID_HANDLE | CLOSED_OR_INVALID_HANDLE | no-op |

上述表适用于参数有效、句柄类型正确的调用。多个错误同时存在时，保留现有 JNI 前置检查顺序并建立基线，不随重构任意改变优先级。错误类型的 void release 不对该实例执行任何状态转移。

#### 6.10.2 out/info 写入规则

| 结果 | out | 非空 info |
|---|---|---|
| READY=1 | 仅写完整有效输出范围 | 写前 8/11 槽位真实信息 |
| OUTPUT_TOO_SMALL=3 | 不修改 | 写前 8/11 槽位 pending 信息，`info[4]` 为所需字节数 |
| NEED_INPUT=0 / END_OF_STREAM=2 | 不修改 | 按现有实现将前 8/11 槽位置零；调用者不可解读成有效帧 |
| JNI 前置校验失败 | 不修改 | 不修改 |
| 进入 session 后的普通负错误 | 不输出部分数据 | 在无 JVM 异常时将前 8/11 槽位置零，不残留上一帧 |
| JVM 数组复制异常 | 内容不可供业务消费 | 保留 JVM 异常，Native pending 不被提交消费 |

非空 info 的多余槽位在任何正常返回路径上均保持原值。前置校验应在推进队列/解码器前完成；`info==null` 仅取消信息复制，不能改变解码推进或返回状态。

#### 6.10.3 需要明确映射的错误

| 场景 | 返回码 |
|---|---|
| 参数/范围/flags 非法，创建时负 epoch | INVALID_ARGUMENT (-1000) |
| full/bridge 中 decoder 后端不可用 | VENDOR_UNAVAILABLE (-1002) |
| 当前进程/构建 ABI 不可用 | VENDOR_ABI_NOT_READY (-1004) |
| 外部模型缺失/损坏/准备 IO 失败 | MODEL_MISSING / MODEL_CORRUPT / MODEL_IO_FAILED (-1010/-1011/-1012) |
| 不支持内容/精度/安全预算 | UNSUPPORTED_MODE (-1020) |
| 非法帧头或 CRC | INVALID_HEADER (-1021)，具体 EOS 多错误优先级按基线 |
| 单次输入超过上限 | INPUT_TOO_LARGE (-1022) |
| EOS 时缺少完整帧 | TRUNCATED_FRAME (-1023) |
| decoder 配置变化 | UNSUPPORTED_CONFIG_CHANGE (-1024) |
| 分帧同步扫描超限 | RESYNC_LIMIT (-1026) |
| 无效、关闭或已释放句柄 | CLOSED_OR_INVALID_HANDLE (-1030) |
| 输入 epoch 不匹配或 flush 未递增 | STALE_EPOCH (-1031) |
| EOS 后继续输入 | INVALID_STATE (-1032) |
| 完整 sample 契约不成立 | COMPLETE_SAMPLE_CONTRACT (-1033) |
| 类型化非 void 接口收到错误句柄种类 | HANDLE_KIND_MISMATCH (-1034) |
| Native 分配失败/句柄空间耗尽 | NO_MEMORY (-1090) |
| 内部状态、输出形状等不可恢复异常 | INTERNAL (-1091) |

`NATIVE_CONTRACT_MISMATCH`、`VENDOR_SYMBOL_MISSING`、`FRAME_DIALECT_NOT_READY` 等已有枚举仍保留；不因表中未逐项触发而删除或复用。公共错误不得承诺能捕获 SIGSEGV 或未改造的源码 exit。

## 七、JNI 实现与错误处理

### 7.1 实现原则

- `JNI_OnLoad` 只注册原有 16 个方法，版本脚本不额外导出算法函数。
- 注册表和锁顺序保持可验证；不将裸内存地址暴露为可任意解引用的 Java 句柄。
- Java/Native 均检查 offset、length、capacity 和整数溢出。
- JNI 字符串、数组和本地引用使用 RAII，C++ 异常不能穿透 JNI。
- `std::bad_alloc` 映射现有 `NO_MEMORY`，其他内部异常映射现有错误，不增加旧客户端无法识别的状态。
- 保留现有 synchronized + Native 实例锁语义，测试 release/flush/receive 并发及句柄类型错误。

Java 边界检查使用防溢出形式，不直接依赖 `offset + length`：

```java
offset < 0 || length < 0 || offset > input.length - length
```

### 7.2 错误映射冻结

- CRC 错误仍映射现有 `INVALID_HEADER`，不新增 CRC 专属错误码。
- 不支持模式/精度/超出已批准位预算仍为 `UNSUPPORTED_MODE`。
- 外部模型缺失/损坏/IO 失败保留 `MODEL_MISSING/MODEL_CORRUPT/MODEL_IO_FAILED`。
- 状态、epoch、句柄类型、完整 sample 和 EOS 错误沿用原映射。
- 旧 loader 专属错误值保留在枚举中，即使静态后端使部分错误不再出现，也不删除/复用编号。
- 可在现有异常 message 和内部诊断日志记录阶段/源错误；不能要求旧客户端解析新的结果结构。

### 7.3 历史缺陷与迁移差异记录

建立明确清单，分别记录：原契约缺陷修复、backend 提供方式变化、模型内嵌带来的内部变化。每项附回归测试，避免以“无缝”为由保留越界、退出进程等问题，也避免以“重构”为由任意改变业务行为。

## 八、单 SO 构建、旧 jniLibs 退出与分发

### 8.1 工具链和源码基线

沿用当前工具链：

```text
minSdk: 24
NDK: 27.2.12479018
CMake: 3.22.1
ABI: arm64-v8a、armeabi-v7a
STL: c++_static
```

参考源码基线为 `e7d244d29454eb04c968cd98a30587303a9c15f8`。使用固定的授权源码快照、显式源码列表和可审计补丁，不让发布构建依赖开发机绝对路径。

建议目录：

```text
vendor/av3adecoder/          授权源码快照（包含内嵌模型）
patches/av3adecoder/         移植、安全化补丁
native/decoder/             静态 target 和安全适配层
native/src/                 原 JNI/core 和新静态 backend
```

不直接沿用源码中的 NDK r20b/硬编码路径 Makefile。标量解码建立基线后再验证 NEON；ARMv7 架构宏不复用错误的 AArch64 定义。

### 8.2 构建和打包唯一来源

```text
冻结 Java/JNI 基线并检查源码/模型
                ↓
每 ABI 编译 avs3a_core + avs3a_reference_decoder 静态对象
                ↓
与 JNI、内嵌模型链接成 libavs3a_jni.so
                ↓
校验导出、依赖、身份、对齐和原 JNI 绑定
                ↓
externalNativeBuild 打包 full AAR
                ↓
校验 AAR/APK 中最终 SO，导出分 ABI 的单 SO 交付物
```

不再有“先构建独立 decoder SO，再 stage 到 jniLibs，最后构建 bridge”的链路。

`full` 由 Gradle/CMake 的 externalNativeBuild 唯一提供 `libavs3a_jni.so`。从 full 打包路径中移除旧的：

```text
sdk/src/full/jniLibs/arm64-v8a/libavs3a_decoder.so
sdk/src/full/jniLibs/armeabi-v7a/libavs3a_decoder.so
```

这里的“替换 jniLibs”是替换实现和依赖来源，不再保留 decoder 文件名，也不再将新 JNI SO 复制回同一 sourceSet 与 externalNativeBuild 重复打包。默认模型 asset 一并退出必需输入。

实际清理时先验证目标绝对路径仅为上述工作区内的旧文件；旧二进制如需留作对照，放在不参与打包的受控测试输入目录，不做宽泛递归删除。

建议交付路径（计划新增）：

```text
dist/full/<version>/arm64-v8a/libavs3a_jni.so
dist/full/<version>/armeabi-v7a/libavs3a_jni.so
dist/full/<version>/avs3a-sdk-<version>.aar
```

符号和摘要另行归档，不是应用运行依赖。bridge/full 各有独立构建目录和清单，防止增量构建串包。

### 8.3 ELF 和最终安装包要求

- SONAME 为 `libavs3a_jni.so`，保留 `AVS3A_JNI_1`/`JNI_OnLoad` 导出约定。
- 除工具链必要的版本元信息外，不新增面向调用者的动态导出符号。
- `DT_NEEDED` 不含 decoder、`libc++_shared.so`、FFmpeg、renderer 等非系统运行库。
- 不允许未满足的依赖，不能通过忽略 undefined symbol 掩盖问题。
- ARM64 的唯一 SO 设置并验证 16KB LOAD 对齐；APK/AAB 的 native ZIP 对齐也要检查。
- CMake 只链接一次模型和 decoder，避免重复模型、重复算法符号或全库链接引入无关组件。
- 保留 unstripped 产物和 build ID，release SO 的 strip 策略不影响 JNI_OnLoad 和身份校验。

### 8.4 身份和 SHA 校验迁移

废弃针对旧 decoder 文件和私有偏移 ABI 的锁定，改为针对源码输入、单 SO 和冻结 JNI 契约的检查。

清单至少包含：源码 commit、补丁摘要、工具链、ABI、编译选项、模型摘要、最终 SO 摘要、build ID、JNI 契约版本。

- `RuntimeVendorVerifier` 的内部实现改为校验当前 `libavs3a_jni.so` 的提供方和实际字节，不查找旧库。
- Native build info 只提供身份信息，不能作为自身 SHA 正确的唯一证据。
- 最终 SO 摘要生成在外部构建清单/SDK Java 内部生成信息中，不把自身摘要反向编入同一个 ELF 形成循环依赖。
- 明确 native 构建、生成校验信息、Java 编译及最终打包的任务依赖，避免使用旧缓存摘要或产生任务环。
- 运行时兼容已提取库、base APK 和 split APK 中的正确 ABI 条目；检查最终实际加载产物，不仅检查源文件。
- 原 `vendorPresent/vendorFingerprintMatched` 等 getter 保留，含义按第六章迁移，不通过常量 true 绕过验证。

### 8.5 CI 改造

- 修改 vendor 输入校验、contract 生成、AAR 校验和发布工作流，使其不再要求独立 decoder SO 或必需 model asset。
- 旧 `abi-contract.json` 的私有偏移证据只作历史记录，不再生成运行时代码；替换为源码 backend 的构建/接口一致性验证。
- `protocol/jni-contract.json` 的现有协议内容保持冻结，CI 使用独立保存的基线比对，防止实现和契约一起被误改后互相通过。
- 保留 frame dialect 的现有对外范围与自动校验。
- full 的 fixture/设备/授权门禁迁移到单 SO 身份，不能继承旧 SO 的验证状态。

## 九、兼容、单 SO 与真实解码验收

### 9.1 兼容性测试分层

| 层次 | 测试内容 |
|---|---|
| Java API 快照 | public 类/方法/字段/枚举、签名和常量不删改，旧客户端二进制可调用 |
| JNI 契约快照 | 原 16 方法、descriptor、static 属性、类名、版本、8/11 槽位不变 |
| 旧 NativeBridge 绑定 | 冻结旧 NativeBridge 类，在 Android 上加载新 SO，逐项调用，不添加任何 native 声明 |
| 业务调用回归 | 原 quick start、模型调用链、session/parser 和 Media3 代码不新增初始化步骤 |
| 状态机回归 | 背压、PTS、epoch=0、完整 sample 补齐、flush/EOS、输出太小、句柄类型和 close |
| 单 SO 独立运行 | 安装包无外置 decoder SO、无必需 model.bin，完成真实 full 解码 |
| 打包与依赖 | 每 ABI 恰好一个 SDK SO，依赖白名单、JNI 导出、16KB 对齐、base/split 加载 |

“旧 NativeBridge 绑定”验证 JNI 本身的兼容；“旧客户端 + 新 SDK”验证业务兼容。不能把它们写成“完整旧 AAR 不变”的错误承诺。

### 9.2 真实解码矩阵

本次强制验收原已支持范围：

- Mono、Stereo、4.0、5.1、7.1、5.1.2、5.1.4、7.1.2、7.1.4。
- NN main/LC、支持的采样率和码率边界、原 source precision 策略。
- 内嵌模型与同版本外部模型两条路径。
- 对 10.2/22.2、对象/混合/HOA、8/24 bit 源精度、非法索引及超限组合保持明确拒绝。
- 通过这些模式的拒绝测试，不代表源码所有对应算法都已完成功能验证。

参考解码基线固定源码、模型、随机实现和优化选项；检查帧数、采样数、通道顺序、PCM 数值、首尾行为及 PTS。同一确定性配置尽量逐样本一致，跨优化差异须提前定义指标，不能测试失败后临时放宽标准。

旧 SO 用于共有模式回归和差异分析，不当作安全性的唯一正确性依据。现有 fixture `NOT_READY`、设备 `NOT_RUN` 状态必须由新真实证据替换，不能仅修改状态字段。

### 9.3 安全与压力

保留源码安全化章节的全部测试要求：随机分片、粘帧、截断、坏 CRC、CRC 正确但内部字段非法、元数据计数越界、位预算边界、内存失败注入、多实例、长期解码及高频创建/flush/close。

分别 fuzz parser 和完整 decoder；使用 ASan/UBSan 等适用工具。JNI 测试必须包括数组边界、异常路径引用释放、release 锁顺序及 pending 输出保留。

设备覆盖 ARM64/ARMv7、最低支持 API 的可用环境及代表性系统版本；ARM64 覆盖 4KB/16KB 页环境。对 split/非提取 native libs 的加载验证不能由普通文件路径测试代替。

### 9.4 发布门禁

1. Java/JNI v2 冻结基线全部通过，包括 16 方法、结果数组和错误码。
2. 原业务调用链、旧客户端二进制与新 SDK 通过测试。
3. full 每 ABI 只有 `libavs3a_jni.so`，无独立 decoder 或 C++ shared runtime。
4. 删除默认 model asset 后仍可通过原 prepareBundledModel/open 调用完成解码。
5. 外部模型接口不是空实现，错误和成功路径均通过。
6. 不再有旧私有结构体偏移访问或 decoder 动态加载。
7. 声明支持的配置有真实 PCM 和设备证据。
8. 安全、并发、资源生命周期、EOS/PTS 和 16KB 验收通过。
9. bridge/full 互斥变体内容正确，bridge 无 decoder/model 且不谎报可解码。
10. 分发授权确认、构建可追溯、符号包齐全；未验证项目不能标为完成。

## 十一、最终交付定义

本次不是“换接口后重新接入”，而是 **以旧接口为边界的内部重实现和单库合并**：

- Java public 调用和 JNI v2 接口保持兼容。
- 每 ABI 只需一个 `libavs3a_jni.so`，包含 decoder 和默认模型。
- 不再携带旧 decoder SO，不再依赖其 SHA、符号或私有偏移。
- SDK 内部 Java 随 AAR 更新，业务代码不需配合迁移。
- 对象/HOA/元数据不得破坏旧槽位语义，不冒充本次已开放能力。
- 发布以兼容性、真实解码、安全性和单 SO 依赖检查的证据为准。

源码采用 UWA Code Sharing Policy，当前分发批准状态为 `false`。合并为单 SO 不改变源码、模型和二进制的授权义务；正式分发仍需确认许可。
